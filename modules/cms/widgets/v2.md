# WidgetEditor (v2) widgets: PHP

The v2 widget system lives beside the v1 system (`Nails\Cms\Widget\WidgetBase`, `cms/widgets/*/widget.php`). This page covers the PHP side: the contract, how classes are found and named, which one wins, nesting, and the limits. The editor screen is [WidgetEditor (v2) editor](editor.md).

v2 widgets are plain PHP classes under a component's `Cms\Widgets` namespace (`App\Cms\Widgets\` in an app). They implement `Nails\Cms\WidgetEditor\Interfaces\Widget` and, usually, extend `Nails\Cms\WidgetEditor\Widget\Base`.

```php
namespace App\Cms\Widgets;

use Nails\Cms\WidgetEditor\Status;
use Nails\Cms\WidgetEditor\Widget\Base;

class Heading extends Base
{
    const ALIASES = ['richtext'];

    protected string $label   = 'Heading';
    protected string $summary = 'A heading with an optional subtitle';
    protected array $defaults = ['sText' => ''];

    public function render(array $data): string
    {
        return '<h2>' . htmlspecialchars($data['sText']) . '</h2>';
    }
}
```

## Status

`Status` is a backed enum. The status controls whether the widget renders and whether the editor offers it.

| Status | Offered in organiser | Existing instances editable | Renders | `cmsWidget()` |
| --- | --- | --- | --- | --- |
| `ACTIVE` | yes | yes | yes | yes |
| `HIDDEN` | no | yes | yes | yes |
| `DEPRECATED` | no | yes, with a warning and `getAlternative()` | yes | yes |
| `DISABLED` | no | no, shown as a locked placeholder, data kept as-is | no | `''` |

Set it with the `STATUS` constant. Each widget declares its own, and a widget does not inherit a status from its parent.

```php
const STATUS      = Status::DEPRECATED;
const ALTERNATIVE = 'App.Cms.Widgets.Heading';
```

## Slugs and aliases

The identity of a widget is its class name. The stored slug is the same name with `\` replaced by `.`:

* `App\Cms\Widgets\Heading` is stored as `App.Cms.Widgets.Heading`
* A legacy slug such as `richtext` contains no `.`, so it never collides with a v2 slug

`Nails\Cms\WidgetEditor\Service\Registry::slugFor()` and `classFor()` convert between the two.

A widget may answer to earlier slugs with `ALIASES`. Use them for renames, moves, and the cut-over from v1, so saved content does not need a data migration first.

```php
const ALIASES = ['richtext', 'App.Cms.Widgets.OldHeading'];
```

Aliases are inherited like any constant. A widget that does not want its parent's aliases must set `const ALIASES = [];`. An alias that two unrelated widgets both claim throws a `RegistryException` when the registry is first used.

The editor opens an instance stored under an alias as the widget that claims it. The instance keeps its stored slug until someone edits it; an edited instance is saved under the canonical slug. When the stored data changed shape too, the widget converts it with `upgrade()` (see [Fields](editor.md#fields)).

`getSlug()` is an instance method. It returns the **canonical** slug, which is the slug of the root of the override chain (see below), so it depends on the class and cannot be static.

## Overrides

Overrides let an app replace a module's widget without changing the module. Discovery builds the registry from every component, in the order `Components::available()` lists them. The app is first, so it has the highest precedence.

A class overrides the class it extends when all of these hold:

* The class and its parent both come from the registry
* The class comes from a component with higher precedence than its parent

Otherwise the class is a separate widget (a variant). Two attributes change the answer:

* `#[Overrides]` forces an override, even from equal precedence
* `#[DoesNotOverride]` keeps a separate widget, even from higher precedence

```php
use Nails\Cms\WidgetEditor\Attribute\Overrides;

#[Overrides]
class Heading extends \Nails\Cms\Widgets\Heading
{
}
```

Rules:

* An override takes the root's canonical slug, so content stored against the root renders the override
* A widget cannot be both `#[Overrides]` and `#[DoesNotOverride]`
* `#[Overrides]` on a class with no registered parent throws
* Two classes that both override the same parent throw

`Nails\Cms\WidgetEditor\Service\Registry::canonicalSlugFor()` returns the canonical slug for a class.

## Nesting

A container widget places children in named slots on its own data. Each slot is an ordinary list of `{slug, data}` instances:

```json
{"slug": "App.Cms.Widgets.Columns", "data": {"left": [{"slug": "richtext", "data": {"body": "<p>Hi</p>"}}], "right": []}}
```

Declare the slots with `getSlots()`, and render them with `renderSlot()` inside `render()`:

```php
public function getSlots(): array
{
    return [
        'left'  => ['label' => 'Left column', 'max' => null],
        'right' => ['label' => 'Right column', 'max' => null],
    ];
}

public function render(array $data): string
{
    return '<div class="cols"><div class="col">' . $this->renderSlot('left', $data) . '</div>'
        . '<div class="col">' . $this->renderSlot('right', $data) . '</div></div>';
}
```

`renderSlot()` renders children in the same mode as the call. `render()` renders children with `render()`, and `preview()` renders them with `preview()`. A widget with no slots is a leaf.

Read every instance in stored JSON, at any depth, with `Registry::walk()`. The callback receives the instance and its path, such as `0.data.left.2` for the third child of the `left` slot of the first top-level instance:

```php
Nails\Cms\WidgetEditor\Service\Registry::walk($aWidgetData, function (object|array $oNode, string $sPath): void {
    // ...
});
```

### Depth

`Nails\Cms\Service\Widget::getMaxDepth()` returns the deepest level that renders. The default is `8`. Top-level instances are depth `0`. An instance deeper than the limit is skipped and renders as an empty string, the same as an unknown slug. It does not throw, so one bad row cannot break a page.

### Instances per area

`Nails\Cms\Service\Widget::getMaxInstancesPerArea()` returns the total number of instances an area may hold, counted at every depth. The default is `200`. The editor enforces this on insert and move, and it ships with the editor. Rendering does not check it.

Override either method on the widget service, the same way as `getWidgetGroupOrder()`:

```php
class Widget extends \Nails\Cms\Service\Widget
{
    public function getMaxDepth(): int
    {
        return 4;
    }
}
```

### Canvas stylesheets

`Nails\Cms\Service\Widget::getCanvasAssets()` returns the stylesheet URLs the editor canvas loads, so previews look like the site. It defaults to none, and the canvas never loads scripts. The canvas ships with the editor.

## Rendering

Use the same helpers as v1. They accept either kind of slug, and a v2 class name:

```php
<?=cmsWidget('App.Cms.Widgets.Heading', ['sText' => 'Hello'])?>
<?=cmsWidget(\App\Cms\Widgets\Heading::class, ['sText' => 'Hello'])?>
<?=cmsWidget('richtext', ['body' => '<p>Hi</p>'])?>
```

Areas and templates render v2 instances through the same path. Unknown slugs render as an empty string (an area outside production still throws, as before). A disabled widget is known but renders nothing.

`Nails\Cms\WidgetEditor\Service\Registry::renderNode()` renders one stored instance. It fires `WIDGET:RENDER:PRE` and `WIDGET:RENDER:POST` with the same arguments as v1 widgets.

## Assets

`getAssets()` returns two lists, `render` (front end) and `editor` (inspector):

```php
public function getAssets(): array
{
    return [
        'render' => [['heading.css', 'CSS']],
        'editor' => [],
    ];
}
```

Render assets load when the widget renders, for the instance and for its children.

## Constructors

Keep constructors free of side effects. The registry builds every widget for the catalogue on each request. Resolve screenshots and other expensive data in the methods that need them.

## API

Admin only (`Nails\Admin\Traits\Api\RestrictToAdmin`). The controller is `Nails\Cms\Api\Controller\WidgetEditor`, at `api/cms/widgeteditor/…`. There is no controller map. The v1 `api/cms/widgets` endpoints are unchanged.

| Method and path | Body | Result |
| --- | --- | --- |
| `GET …/catalogue` | — | Widgets, groups, favourites, limits, canvas stylesheets |
| `POST …/preview` | `{"context": {}, "items": [{"slug", "data"}]}` | `[{slug, html, error}]`, one per item, in order |
| `POST …/inspector` | `{"items": [{"slug", "data"}]}` | `[{slug, type, html, assets, error}]` for HTML-form inspectors |
| `PUT …/favourite/{slug}` | — | Adds the slug. Sending it again changes nothing |
| `DELETE …/favourite/{slug}` | — | Removes the slug. Sending it again changes nothing |
| `PUT …/favourites` | `{"slugs": ["a", "b"]}` | Replaces the user's list, in that order |
| `PUT …/version` | `{"version": "v1"}` or `{"version": "v2"}` | Stores which editor this browser session opens |

`GET …/catalogue` takes the area rules as a JSON `rules` query parameter: `{"allowed": ["richtext", "group:Text"], "disallowed": ["App.Cms.Widgets.Old"]}`. An entry is a slug (aliases count) or `group:<label>`. `allowed` is applied first, then `disallowed` removes from what remains. Omit `rules` to list every widget the editor can place. An empty `allowed` list offers nothing.

Widgets with no groups of their own are listed under `Generic`, and `group:Generic` matches them.

Disabled widgets are left out. Hidden and deprecated widgets are included, with `status`. Each widget carries its label, text, icon, groups, keywords, aliases, slots, defaults, asset URLs (not tags), and an inspector descriptor: `fields` plus the schema, or `html`. A URL screenshot is used as given. A CDN object id is cropped to 120×120 for the list and 400×400 for the detail.

The payload includes `revision`, a hash of the rest. The API always sends `Cache-Control: no-store`, so the editor compares `revision` instead of caching the response.

Preview renders with `preview()`, in preview mode, and loads no assets. One item throwing does not fail the batch: that item comes back with `html` empty and `error` set. An unknown slug comes back with empty HTML and no error. `context` is the preview context (`record_type`, `record_id`, `locale`, `area`, `slot_path`); a widget reads what it needs.

`POST …/inspector` is only needed for HTML-form widgets. A fields-schema widget comes back as `type: fields` with no HTML, because the catalogue already has the schema. A disabled or unknown slug comes back with `error` set.

A request may carry at most 1000 items.

### Favourites

Stored in `{{NAILS_DB_PREFIX}}cms_widget_favourite`: `id`, `user_id` (foreign key to `user`, `ON DELETE CASCADE`), `widget_slug`, `sort_order`, `created`. The column is `sort_order` rather than `order`, which is reserved in MySQL. Rows, not a JSON blob, so a slug remap can update them. A user may store 500.

`Migration12` creates the table. It is repeatable and does nothing when the table is already there, so an app that skips the number still gets it.

When user accounts are merged, `Nails\Cms\Event\Listener\User\Merge\Pre` moves the merged users' favourites onto the user who is kept, before those users are deleted. The kept user's row wins when both sides have the same slug.

Group collapse and recently used widgets are not in this table. They live in the browser.

## Monitor

The monitor counts v2 widgets with `Nails\Cms\WidgetEditor\Monitor\Adapter`, which implements the v1 `Nails\Cms\Interfaces\Widget` interface, so existing mappers accept it. The adapter needs no change in app mappers. Usages are counted for the canonical slug and for each alias, and the totals are summed. See [Monitor](../monitor.md).

## Bridging v1 widgets

A bridge is a v2 class that delegates to an existing v1 widget. The v1 class keeps doing the work: its `render()`, editor form, assets, `dropped` and `removed` scripts, and its metadata are used as they are. Stored content keeps the v1 slug, which the bridge answers to through an alias, so nothing is migrated first.

Generate one bridge per v1 widget with the console:

```bash
php ./vendor/nails/module-console/console.php cms:widgets:bridge --dry-run
php ./vendor/nails/module-console/console.php cms:widgets:bridge --slug=FAQBlock
```

Without `--slug` every v1 widget is bridged. A bridge is written to `src/Cms/Widgets/<Slug>.php` in the app and is never overwritten. Review each generated class before you rely on it.

When a v2 widget already claims the slug (a module ships one, such as `Area`), the bridge overrides it instead: the generated class is `#[Overrides]` and extends that widget. The two never claim the same alias, which would fail the whole catalogue with a `RegistryException`. The override keeps the v2 widget's render, and the v1 class the bridge delegates to still decides the editor, scripts and status:

```php
namespace App\Cms\Widgets;

use Nails\Cms\WidgetEditor\Attribute\Overrides;
use Nails\Cms\WidgetEditor\Traits\Legacy;

#[Overrides]
class Area extends \Nails\Cms\Cms\Widgets\Area
{
    use Legacy;

    protected static function legacyClass(): string
    {
        return \App\Cms\Widget\Area::class;
    }
}
```

A generated bridge looks like this:

```php
namespace App\Cms\Widgets;

final class FAQBlock extends Base
{
    use Legacy;

    protected static function legacyClass(): string
    {
        return \App\Cms\Widget\FAQBlock::class;
    }
}
```

The bridge maps the v1 metadata onto the v2 surface:

* The stored slug (the v1 folder name) becomes an alias, so existing content resolves
* `disabled`, `deprecated` and `hidden` map to `Status::DISABLED`, `DEPRECATED` and `HIDDEN`, in that order of precedence
* The v1 description is used as both the summary and the description; the v1 grouping becomes the one group; v1 keywords (a comma separated string) are split
* The v1 editor form is the HTML inspector

Render assets are not loaded in the canvas, so only the editor assets are returned.

### Shipped widgets

`module-cms` ships v2 classes that keep the v1 stored keys and slugs, so existing content renders without a data migration:

| Widget | v2 class | How |
| --- | --- | --- |
| Rich Text (`richtext`) | `Nails\Cms\Cms\Widgets\Richtext` | Native: a `richtext` field |
| Plain Text (`html`) | `Nails\Cms\Cms\Widgets\Html` | Native: a `textarea` field, output as stored |
| Blockquote (`blockquote`) | `Nails\Cms\Cms\Widgets\Blockquote` | Native: a `richtext` quote and two text fields |
| Table (`table`), Tabs (`tabs`), Accordion (`accordion`), CMS Area (`Area`) | `Nails\Cms\Cms\Widgets\*` | Bridged to the v1 widget |

The bridged widgets keep their v1 editors. A table is a grid, Tabs and Accordion store parallel `title` and `body` lists, and an Area is chosen from a picker, and none of those is a field type yet. Tabs and Accordion can move to a repeater later. That needs the stored lists converted first, and the inspector reads stored data as it is, so the conversion must ship with the change.

The v2 Blockquote links its citation when there is a URL. The v1 view did the reverse, so v2 output differs from v1 for a citation with a URL.

**Gap:** the bridge command reads the v1 widgets that are not disabled, so a widget disabled in v1 gets no bridge. An app that disables a shipped widget in v1 must also override its v2 class to disable it (`Status::DISABLED`), or the v2 editor offers it.

### Scripts

A v1 `dropped` script runs once its form is in the inspector, and a `removed` script runs before the widget is removed. Both run with `domElement`, the jQuery root of the form, as their argument, and with `window.NAILS.ADMIN.refreshUi` available as in v1. `this` is an empty object; no shipped v1 widget uses it. Scripts run in the inspector only, not in the canvas. A `dropped` script that throws is reported as a warning above the form. A `removed` script that throws is logged to the console, and the widget is still removed.

### Remapping stored slugs

Content stored under a slug that is renamed (for example, a v1 widget moved to a new v2 class) is rewritten by a migration that uses the `RemapWidgetSlugs` trait:

```php
namespace App\Database\Migration;

use Nails\Cms\WidgetEditor\Traits\Database\Migration\RemapWidgetSlugs;
use Nails\Common\Console\Migrate\Base;

// Name the class with the next unused number for the app (see Migrations)
class Migration1 extends Base
{
    use RemapWidgetSlugs;

    public function execute()
    {
        $this->remapWidgetSlugs(
            '{{NAILS_DB_PREFIX}}cms_area',
            'widget_data',
            ['richtext' => 'App.Cms.Widgets.Richtext'],
        );
    }
}
```

The method returns `['rows' => …, 'nodes' => …, 'invalid' => …]`: rows changed, nodes rewritten, and rows whose JSON could not be decoded. Invalid rows are skipped and not changed. Pass `$bDryRun = true` to count without writing. The walk changes only the `slug` of an instance, at any depth, and leaves every other value alone.

### Not in this release

* **Port mode**: generating a v2 class with `getFields()` from a v1 `editor.php` is not built. A bridge stays on the v1 form until it is ported by hand.
* **Remap scaffolding**: the console does not yet write a remap migration for you; write one as above.

## Limits

* The [editor](editor.md) edits areas and HTML-form widgets. The canvas and the fields-schema controls are separate pieces, and they are not described here yet.
* A widget whose inspector needs a control no field type provides uses an HTML form for the whole inspector. An app or module can add the type instead (see [Field types](editor.md#field-types)).
